# Plan — "Services" module (MariaDB / MySQL / PostgreSQL databases)

Version 3 (2026-11-04) — **implemented** on the `feature/services` branches (API, interface, CLI). This document keeps the history of the decisions; the up-to-date reference is the managed services section of `CLAUDE.md`. Implementation deviations are in §12bis and §14.

---

## 0. Decisions (approved on 2026-11-04)

- **D1**: one global instance per engine + major version, shared by all the databases of all the sites (not one instance per stack; better efficiency). PG 16 and PG 17 can coexist. The instance is created with the 1st database and retired after the last one.
- **D2**: the user did not decide; the chosen default is to **purge** the data of a retired instance (it only contains the system catalog; keeping it would desynchronize the admin password when the instance is recreated). Option `SERVICES_ARCHIVE_ON_RETIRE=true` renames it to `…-retired-<ts>` instead.
- **D3**: `svc-` prefix.
- **D4**: passwords are always generated by the server and shown only once.
- **D5**: admin only.
- **D6**: MCP tools never return a password.
- **D7**: shared network `loch-services` (`internal`) for the MVP; isolation between sites = authentication, flagged in the UI.
- **D9**: MySQL added as a 3rd engine (`mysql`), versions **8.4** (LTS) and **5.6** (end of life since 2021, offered anyway: `Deprecated=true`, warning in the UI). See §5bis.
- **D10**: exposure of external ports is **configured in the `.env`** (`SERVICES_EXPOSED_PORTS`, port per engine + version); the web interface shows it read-only, with no way to change it. See §6bis. **Reversed by §18** (2026-11-05): ports are chosen per instance in the panel, within a policy set in the environment.
- **D8**: MariaDB: **`GRANT ALL PRIVILEGES ON \`db\`.*`** (includes `LOCK TABLES`, `TRIGGER`, `EVENT`, which CMSs need); no global privilege (FILE, SUPER, GRANT OPTION are excluded as a result).

**Consequences for the plan:**
- Secret: 0400 owned by the API (root) is enough; **no chown of the secret**. `SecretOwner()` removed from the contract.

- MySQL family (MariaDB + MySQL): **uniform** admin access through `["sh","-c","MYSQL_PWD=\"$(cat /run/secrets/admin_password)\" exec <bin> -uroot -N -B"]` (constant string, SQL on stdin). `MARIADB_MYSQL_LOCALHOST_*` variables dropped. The API never reads the secret.

- MySQL 5.6: the 767-byte index limit in utf8mb4 cannot be worked around on the server side → documented (`ROW_FORMAT=DYNAMIC` tables or `varchar(191)`), shown in the UI with the end-of-life warning.
- Startup in 5 to 11 s excluding the pull: **synchronous** creation is confirmed (pull outside the lock).

## 2. Model

| Item | Value |
|---|---|
| Instance ID | Provided by the engine (`Engine.InstanceKey`). For PG and MariaDB: `<engine>-<versionSlug>` → `postgres-16`, `mariadb-11-4` |
| Project, directory, `container_name` | `svc-postgres-16` |
| Compose | `$HOSTING_STACKS_DIRECTORY/svc-postgres-16/{compose.yaml, .loch-managed, secrets/admin_password}` |
| Data | `$SERVICES_DATA_DIRECTORY/svc-postgres-16/` (default `/data/services`), long bind with `create_host_path: false` |
| Network | `loch-services`, external and `internal`. Alias = container name. No published port |
| "Database" resource | Name `^[a-z][a-z0-9_]{0,31}\z`, with a dedicated user of the same name and privileges on its own database only |

**Source of truth.** There is no loch store.
- **Instances**: scan of the `svc-*` directories that carry the marker and a valid `x-loch`.
  - The image, the data path and the name are **recomputed from the ID**, never read from the compose file.
  - The compose file is compared with the expected rendering. A difference gives `modified`, and destructive operations are then refused.
- **Databases**: read from the engine catalog.
  - A database created outside loch is marked `managed=false`. It blocks the retirement of the instance, and both its drop and its reset are refused.
  - If the instance is stopped or unhealthy, the list is `databases: null` and operations return `503 NOT_READY`. An instance is never retired without being able to read its catalog.

**Admin password.**
- Generated with crypto/rand and written atomically to `secrets/admin_password` (0400, in a `secrets/` directory with mode 0700).
- Mounted as a compose secret. The `POSTGRES_PASSWORD_FILE` and `MARIADB_ROOT_PASSWORD_FILE` variables point to it.
- Never placed in `environment`, never returned, never read by the API: operations go through the local socket.

## 3. Modular architecture (Go)

### 3.1 `internal/composekit/`: mechanical refactor in a separate PR

Extracted content:
- `ExecRunner`, `tailBuffer`, `dockerEnv`;
- `UpArgs` / `DownArgs` (the compose file name becomes a parameter);
- `RealDir`, `EnsureDir`, `WriteFileAtomic`, `ReadFileNoFollow`, `IsRegularFile`, `ManagedMarker`;
- `CheckWritableDir`, `CheckSamePathMount`, `SelfInspector`;
- a `Semaphore` **shared** with hosting (4 compose operations in total);
- `composekittest.FakeRunner`.

Out of scope: `stamp.go` and `operations.go`, which stay in hosting.

Acceptance criterion: the existing hosting tests pass **without any change**. Aliases are kept in hosting.

### 3.2 `internal/docker/exec.go`

```go
type ExecRequest struct { Cmd []string; User string; Stdin []byte }   // no user Env
type ExecResult  struct { ExitCode int; Stdout, Stderr []byte }       // capped at 1 MB / 64 KB
func (c *Client) ExecRun(ctx context.Context, containerID string, req ExecRequest) (ExecResult, error)
```

Sequence: `ExecCreate` → `ExecAttach` → stdin written in a goroutine, then `CloseWrite` (to avoid a deadlock) → bounded `stdcopy` → `ExecInspect`.
Limits: 30 s timeout per exec, stdin capped at a few KB.

### 3.3 `internal/services/`: generic contract

The object handled is a "resource". The word "database" only appears in the user interface.

```go
type Lifecycle int
const (
    OnDemand Lifecycle = iota // instance created with the 1st resource, retired with the last one (PG, MariaDB)
    Explicit                  // the instance is the resource (Meilisearch, simple Redis)
)

type Version struct {
    Version, Image, SupportUntil string
    DataMount string // property of the version (PG18: /var/lib/postgresql)
    Deprecated bool
}

type Engine interface {
    ID() string
    Kind() string          // "database", later "cache", "search"…
    DefaultPort() int
    Lifecycle() Lifecycle
    Versions(now time.Time) []Version
    InstanceKey(version string) string
    Render(inst InstanceRef, cfg RenderConfig) ([]byte, error) // full compose, deterministic
    DataOwner() (uid, gid int) // pre-chown of the data directory (PG 18 requires it)
}

type Credentials []Field // ordered: host, port, database, user, password, uri

// Optional capability. Execution (docker exec, HTTP…) is internal to the engine.
type Provisioner interface {
    ValidateName(name string) error
    List(ctx context.Context, t Target) ([]Resource, error)
    Provision(ctx context.Context, t Target, name string) (Credentials, error)
    Deprovision(ctx context.Context, t Target, name string) error
    RotateSecret(ctx context.Context, t Target, name string) (Credentials, error)
}
```

`Target` designates the **verified** container (see §5, E3) and pairs it with an executor.
File layout:
- `engines/postgres/` and `engines/mariadb/` use `ExecRun`;
- a future Meilisearch engine would use HTTP;
- an engine without a `Provisioner` only exposes instances.

Shared files: `registry.go`, `manager.go`, `instances.go`, `resources.go`, `locks.go`, `preflight.go`, `validate.go`, `errors.go`.

### 3.4 Manager and concurrency

- A global `mu` to reserve a directory (`os.Mkdir`), plus a **lock per instance**:
  - channel of size 1, waiting under a context;
  - injectable wait timeout (30 s by default), after which the operation returns `OPERATION_IN_PROGRESS` 409;
  - entry removed on retirement (no map that grows forever).
- **Creation** (synchronous, `context.WithoutCancel`, 5 min):
  1. Validation, then **image pull outside the lock**.
  2. Lock taken, then `ensureInstance`:
     - Mkdir;
     - check that no container or project with the same name exists;
     - empty data directory, otherwise `DATA_DIR_NOT_EMPTY`;
     - write the secret, the compose file, then the marker;
     - `up -d --wait`.
  3. Container verification, `List` (`RESOURCE_EXISTS`), `Provision`.
  4. **Rollback only if the instance was created by this same operation.** A test checks that an existing instance is never purged.
- **Deletion**:
  1. `Deprovision`, then `List`.
  2. If the result is 0 databases (neither managed nor unmanaged): `compose stop` right after this re-read, to close the race window, then `down --remove-orphans`, data purge (recomputed path, `Lstat` of the parents), and removal of the stack directory last.
  3. If the re-read fails, the instance is kept (safe by default).
  4. If `down` or the purge fails, the marker stays in place: a new attempt finishes the work.
- **API startup**: **no automatic purge**. Interrupted operations produce a warning.
- **`DELETE /services/instances/{id}`**: retires an empty or orphaned instance explicitly. Refused if the engine is unreachable.
- **Limit**: `SERVICES_MAX_RESOURCES_PER_INSTANCE` (default 50).

```yaml
    networks: {services: {aliases: [svc-postgres-16]}}
    healthcheck: {test: ["CMD","pg_isready","-U","postgres","-h","127.0.0.1"], interval: 5s, timeout: 5s, retries: 30, start_period: 60s}
    mem_limit: 1g        # hard-coded default values; the compose file stays editable
    pids_limit: 512
    shm_size: 256m
    security_opt: ["no-new-privileges:true"]
    logging: {driver: json-file, options: {max-size: 10m, max-file: "3"}}

```

Content of `pg_hba.conf`:
```
local all all trust
host all postgres all reject
host all all all scram-sha-256
```
The superuser therefore cannot connect over the network (no `COPY PROGRAM` that can be exploited remotely).

For MariaDB: `MARIADB_ROOT_PASSWORD_FILE`, `MARIADB_AUTO_UPGRADE=1`, mount on `/var/lib/mysql`, `healthcheck.sh`, bounded `max_connections`.

## 5. Security, after the review

- **No shell**: `Cmd` is a fixed array. SQL goes through **stdin**, never through argv or the environment.
  - PG: `psql -X -q -v ON_ERROR_STOP=1 -At -U postgres -d postgres -f -`, as `postgres`.
  - MySQL family (MariaDB and MySQL): `["sh","-c","MYSQL_PWD=\"$(cat /run/secrets/admin_password)\" exec <mariadb|mysql> -uroot -N -B"]` — constant string without interpolation, validated by the spike; the admin password appears neither in argv nor on the API side (only in the environment of the exec process, inside the container).
- **Rules for calling `docker.ExecRun`** (step 2, delivered):
  - `ErrExecTimeout` and `ErrExecStillRunning` mean "unknown state". Docker does not kill an exec, so the command may have succeeded. The real state is checked (catalog, connection with the new password) before answering; there is never any blind compensation.
  - Each command is bounded on the container side:
    - `timeout -s KILL <n>` at the head of `Cmd`, or `exec timeout …` in the constant `sh -c` string, if the binary exists in the image (to check in the spike);
    - at the head of the SQL: `SET statement_timeout` / `lock_timeout` (PG), `SET SESSION max_statement_time` (MariaDB) or `max_execution_time` (MySQL 8.4).
  - `Stdout` and `Stderr` can echo the input: they are never logged or returned raw. Only the SQLSTATE or the error code is extracted from them. `ExecResult` already masks these two fields in `%v`.
  - The instance lock serializes the execs of the same instance: no concurrent execs and no overlapping retries.
- **Identifiers**:
  - regex anchored with `\z` (the trap: `$` accepts a trailing `\n`);
  - reserved names: `postgres`, `template0/1`, `root`, `mysql`, `mariadb.sys`, `sys`, `information_schema`, `performance_schema`, `public`, `admin`, `loch`, `none`, `all`, `default`, `test`, `user`, `current_user`, `session_user`, `repl`, `replicator`, `healthcheck`, as well as the `pg_` and `mariadb` prefixes;
  - `quoteIdent` **panics** if the name is invalid.
- **C1, `_` wildcard in MariaDB GRANTs.**
  - `GRANT … ON \`my\_ql\`.*`: `_` is escaped as `\_` by `quoteGrantDB`.
  - Any name that, with `_` taken as a wildcard, would match a system database or an existing database is also refused.
  - Integration test: a `my_ql` database must not give access to `mysql`, and `a_b` must not give access to `axb`.
- **E1, password in the engine logs.**
  - PG: the **SCRAM-SHA-256 verifier is computed in Go** and passed in `PASSWORD 'SCRAM-SHA-256$4096:…'`, with RFC 7677 test vectors.
  - MariaDB: `IDENTIFIED VIA mysql_native_password USING '*<hash>'`, with a hash computed in Go.
  - The plaintext password therefore never reaches the engine.
  - Stderr is never logged raw: only the SQLSTATE or the error code is kept.
- `quoteLiteral` **panics** on any character outside `[A-Za-z0-9$:+/=*]`, which makes it independent of `NO_BACKSLASH_ESCAPES`.
- **E3, spoofed target container.** Before each exec, the following is checked:
  - exactly one container matches the `svc-<id>` project and the `db` service;
  - its exact name;
  - its image (in the allowlist);
  - `working_dir` = the expected directory;
  - the source of the data mount = the recomputed path;
  - the `sh.loch.instance` label.
- **E4, marker forged by the CI**: the compose file is compared with the expected rendering, otherwise refused. Option: an HMAC in the marker, with a key derived from `COOKIE_SECRET`.
- **PG privileges**:
  - at instance creation: `REVOKE CONNECT ON DATABASE postgres, template1 FROM PUBLIC` and `REVOKE CREATE ON SCHEMA public FROM PUBLIC` (in template1);
  - per database: `CREATE ROLE "x" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS CONNECTION LIMIT 50 PASSWORD '<scram>'`, then `CREATE DATABASE "x" OWNER "x" TEMPLATE template0`, then `REVOKE ALL ON DATABASE "x" FROM PUBLIC`;
  - on failure: compensation by dropping the role.
  - Deletion: `DROP DATABASE … WITH (FORCE)` then `DROP ROLE`.
- **MariaDB privileges**:
  - `GRANT ALL PRIVILEGES ON <escaped database>.*` (D8), without `WITH GRANT OPTION`, no global privilege;
  - `WITH MAX_USER_CONNECTIONS 50`;
  - on failure: compensation by dropping the database;
  - a user with the same name on another host gives `NOT_MANAGED`.
- **Data**: directory created with mode 0700 and pre-chowned to `DataOwner()` by the API.
- **Purge**: the API runs as root (no `USER` in the Dockerfile). This is documented as a prerequisite and checked by the preflight. `RemoveAll` goes through `unlinkat` and does not follow symbolic links; the parents are checked with `Lstat` and `realDir`.
- **Responses**: `Cache-Control: no-store` and `Pragma: no-cache`. Audit without passwords. Non-admins are refused even with the scope (the test is on the profile, not on the key).

## 5bis. MySQL engine

- Shared package `engines/mysqlfamily/` (compose rendering, SQL, quoting, `_` escaping in GRANTs, native hash) parameterized by a `Dialect`; `engines/mariadb/` and `engines/mysql/` only declare their differences. This is the first real test of the modularity.
- Official images `mysql:8.4` (started with `--disable-log-bin`), `mysql:5.6` (`--innodb-large-prefix=1 --innodb-file-format=Barracuda --innodb-file-per-table=1`). Mount `/var/lib/mysql`, `MYSQL_ROOT_PASSWORD_FILE`, bounded `max_connections`, `mysqladmin ping` healthcheck.
- Admin access: no socket user in the MySQL image → `sh -c` exec with a **constant string** that reads the secret inside the container (`MYSQL_PWD`, never in argv, never on the API side). SQL stays on stdin.
- Privileges: `GRANT ALL PRIVILEGES ON <escaped database>.*` (D8), `_` escaped as for MariaDB.
- Dialect differences:

| | MySQL 8.4 | MySQL 5.6 |
|---|---|---|
| Auth plugin | `caching_sha2_password` (`mysql_native_password` is disabled by default in 8.4) | `mysql_native_password` |
| User creation | `CREATE USER 'x'@'%' IDENTIFIED BY '<plaintext>'` through stdin (`caching_sha2` hash not computed in Go for the MVP; the server does not log failed queries, `general_log` disabled) | `CREATE USER 'x'@'%' IDENTIFIED BY PASSWORD '*<hash>'` (hash computed in Go) |
| Password change | `ALTER USER 'x'@'%' IDENTIFIED BY '…'` | `SET PASSWORD FOR 'x'@'%' = '*<hash>'` |
| User deletion | `DROP USER IF EXISTS` | `DROP USER` after an existence check (no `IF EXISTS` in 5.6) |
| Character set | `utf8mb4` / `utf8mb4_0900_ai_ci` | `utf8mb4` / `utf8mb4_unicode_ci`; start with `--innodb-large-prefix=1 --innodb-file-format=Barracuda --innodb-file-per-table=1` (767-byte index limit otherwise) |
| Connection limit | `WITH MAX_USER_CONNECTIONS 50` | same (`WITH` clause of `GRANT` in 5.6) |
| Architectures | amd64, arm64 | **amd64 only** |

- MySQL 5.6: amd64-only image; on an arm64 host it runs through the compatibility layer (amd64 emulation, `platform: linux/amd64` in the compose file) — user decision. The preflight checks that amd64 emulation is available (otherwise the version is hidden, with a warning at startup); the UI shows "emulated, slower". No security fixes ever: permanent warning in the UI and the CLI.

## 6bis. Exposure of external ports (D10) — configured in the `.env`

> **Superseded by §18.** `SERVICES_EXPOSED_PORTS`, `SERVICES_PUBLISH_ADDRESS` and `SERVICES_TLS_OPTIONAL` were removed: exposure is chosen in the panel, bounded by `SERVICES_EXPOSE_ALLOWED_CIDRS`, `SERVICES_ALLOW_PUBLIC_BIND`, `SERVICES_TLS` and `SERVICES_ALLOW_TLS_OPTIONAL`. The validation, rendering, fail-closed application and hardening below still apply.

Version 2, revised after the security review. Port publishing was tested on 2026-11-04: **a container attached only to the `internal` network publishes no port**; a routable network must be added to it.

**Need.** The `.env` states, for each engine + version pair, whether the instance is reachable from outside and on which host port. **The web interface allows no change**: it only shows the state. By default, nothing is exposed. An instance always stays reachable through `loch-services` and through `loch proxy`.

### Variables
```dotenv
# <instance>=[<address>:]<port>, comma-separated. IPv6 in brackets: postgres-17=[::1]:5417
SERVICES_EXPOSED_PORTS=postgres-16=5416,mysql-8-4=203.0.113.10:3384
SERVICES_PUBLISH_ADDRESS=127.0.0.1    # default address
SERVICES_ALLOW_PUBLIC_BIND=false      # required (true) for any non-loopback address
SERVICES_PUBLIC_HOST=db.example.com   # display and certificate SAN
SERVICES_TLS=auto                     # auto = TLS as soon as an instance is exposed outside loopback; off = TLS disabled everywhere (deliberate choice)
SERVICES_TLS_CERT_FILE=               # optional: verifiable certificate (e.g. ACME) instead of the self-signed one
SERVICES_TLS_KEY_FILE=
```

### Strict validation
On error, **the Services module is disabled** with a clear message in the logs and in `GET /services/config`. The rest of the panel keeps running. The same rule applies to all `SERVICES_*` configuration errors.

Format:
- address parsed by `netip.ParseAddr`, IPv6 must be in brackets;
- more than one `:` without brackets: refused;
- refused: zones (`%eth0`), IPv4-mapped addresses (`::ffff:`), multicast, link-local, host names;
- port parsed by strict `strconv.ParseUint(…,10,16)`, which refuses `05416`, `+5416` and spaces;
- refused: duplicate key, trailing comma.

Content:
- the instance key must be known and enabled in the registry;
- port between **1024 and 32767**, to stay outside the Linux ephemeral range;
- reserved ports: 22, 80, 443, 2375, 2376, 2538 (API), `SFTP_PORT`, and the SFTPGo ports (8080 and web);
- no duplicate port, **including overlapping addresses** (`0.0.0.0:p` against `127.0.0.1:p`, `::` against `0.0.0.0`);
- a non-loopback address requires `SERVICES_ALLOW_PUBLIC_BIND=true`; a specific IP is preferred to `0.0.0.0` or `::`;
- **MySQL 5.6: loopback only** (`127.0.0.1` or `::1`), with no exception possible. For remote access: `loch proxy` or an SSH tunnel;
- `SERVICES_PUBLIC_HOST` must be a valid host name or IP, without a scheme, without `/` and without control characters.

### Rendering: dedicated files, fully managed by loch
- `compose.yaml`, which the admin can edit, **never** contains the exposure.
- The exposure is rendered in **`compose.override.yaml`**. `docker compose up -d` loads it automatically, which allows starting without loch. `ExecRunner` passes `-f compose.yaml -f compose.override.yaml` explicitly.

  Content of the override:
  - `ports: ["<address>:<port>:<containerPort>"]`;
  - a **`pub`** network specific to the instance, declared in the override and created by compose (not `internal`, no other member);
  - the engine TLS options and the `certs/` mount;
  - the anti-exhaustion settings (see below).
- `pg_hba.conf` and `certs/` are also regenerated by loch.
- `modified` detection only covers `compose.yaml`. The override is always rewritten: **closing a port therefore works even if the admin edited the compose file** (no fail-open). If the main compose file no longer starts with the override, the error is visible on the instance (`exposureError`).
- Documented risk: the `pub` network opens Internet egress for the container. Optionally, an outbound `DOCKER-USER` rule is provided in the documentation.

### Application
- **At creation** of an instance: the override is rendered right away.
- **At API startup**: for each managed instance whose expected override differs from the current override:
  1. **All** rendered files are backed up (override, `pg_hba.conf`, `certs/`).
  2. The new files are written.
  3. `up -d --wait`, under lock, **one instance after the other**. The container is recreated, the data is kept and the downtime lasts a few seconds.
  4. `service exposure applied` is audited (before/after), and a log line notes whether the image was updated in the meantime.
- **On failure** (port taken by a process outside Docker, which cannot be detected before `up`):
  - all files are restored and `up` is run again;
  - `.loch-exposure-failed` is written, containing the hash of the target rendering;
  - **no new attempt as long as the `.env` does not change**, to avoid downtime at each restart;
  - the error is visible on the instance.
- Ports already published by another Docker container are detected before `up`: the instance is not touched and the `SERVICE_PORT_IN_USE` code is attached to the instance.

### Hardening
- **Docker bypasses `ufw` and `firewalld`.** Hence the `SERVICES_ALLOW_PUBLIC_BIND` opt-in, a warning at startup for each public bind, and the documented `DOCKER-USER` rule to filter by source (`iptables -I DOCKER-USER -i <ext> ! -s <cidr> -p tcp --dport <port> -j DROP`). The panel cannot set this rule from its container.
- **MySQL-family root limited to localhost in all cases** (from step 4): `MARIADB_ROOT_HOST=localhost` and `MYSQL_ROOT_HOST=localhost`. Integration test on the 5 versions: `SELECT user,host FROM mysql.user WHERE host='%'` returns no system account.
- PG: `host all postgres all reject` stays at the top of `pg_hba`.
- **Deliberate disabling: `SERVICES_TLS=off`** (accepted values: `auto` by default or `off`; any other value disables the module).
  - Applies **to all instances**, exposed or not: no certificate, no `ssl=on`, no `hostssl`, no `REQUIRE SSL`.
  - At the next startup, managed accounts go back to `REQUIRE NONE` and the override is rendered again, through the usual application mechanism.
  - Consequence: passwords and data travel in plaintext on ports exposed outside loopback. A warning is shown at each startup for each affected instance, and the interface shows an "Unencrypted" tag with a tooltip.
  - Q-TLS no longer applies in this mode.
  - The other protections stay active: `SERVICES_ALLOW_PUBLIC_BIND` opt-in, MySQL 5.6 limited to loopback, `root` limited to localhost, PG superuser rejected over the network.
- **TLS in `auto` mode, as soon as an instance is exposed outside loopback:**
  - **PG**: `ssl=on`, and `hostssl all all all scram-sha-256` for the **whole** instance, with no per-subnet rule (the `loch-services` subnet is not stable, and the source can be the `docker-proxy` gateway). Internal sites keep working, because `sslmode=prefer` is the client default.
  - **MySQL family**: TLS **per account** (`ALTER USER … REQUIRE SSL`), not through `require_secure_transport`, which does not exist in 5.6 and would apply to the whole server. This setting is applied or removed at startup on the managed accounts of the instance, and as soon as they are created. Consequence: see question **Q-TLS** below.
  - **Certificate**: self-signed per instance, SAN = `SERVICES_PUBLIC_HOST`, valid for 1 year, renewed at startup if less than 30 days remain. `SERVICES_TLS_CERT_FILE`/`KEY_FILE` can also be provided. Files as `999:999` / 0400 (PostgreSQL requires the key to be owned by the server account).
  - The connection sheet shows the **SHA-256 fingerprint** of the certificate. A self-signed certificate protects against passive eavesdropping, not against MITM. With a verifiable certificate, the sheet offers `verify-full` / `VERIFY_IDENTITY`.
- **Anti-exhaustion**, because the real risk is DoS rather than brute force (generated passwords are strong):
  - PG: `authentication_timeout=10s`;
  - MySQL family: `skip_name_resolve=ON` and a high `max_connect_errors` (through `docker-proxy`, the source is the gateway and a block would hit everyone);
  - per-account limits kept.
- **Loopback does not mean "nobody else".** `127.0.0.1` stays reachable by host processes and by containers in `network_mode: host`. The preflight emits a warning if the Docker version is vulnerable to `route_localnet`, and `network_mode: host` stays forbidden in hosted stacks (rendering controlled by loch).

**Q-TLS — decided on 2026-11-04: simple option chosen.** Exposing a MariaDB or MySQL instance outside loopback makes TLS mandatory for all its accounts, **including those of internal sites**. In PHP, this requires enabling TLS on the client side (`PDO::MYSQL_ATTR_SSL_CA`, or `MYSQL_ATTR_SSL_VERIFY_SERVER_CERT=false`).
- *Recommended, simple*: apply this rule and document it.
- *Alternative*: two accounts per database, `x@<fixed loch-services subnet>` without TLS and `x@'%'` with `REQUIRE SSL`. The subnet must then be fixed (`SERVICES_NETWORK_SUBNET`), which doubles account management.

## 12bis. Step 3 delivered (2026-11-04): deviations from the plan

On the `feature/services` branch of `host-panel-api` (not committed), in `internal/services` and `internal/services/postgres`.

Changes decided during implementation and reviews:
- **Unknown outcome** (`ErrOutcomeUnknown`): it is never treated as a success. The engine finishes what it can (for PG, it "opens" the database if it exists). What remains visible, an orphaned role for example, shows up in `List` and can be deleted.
- **PG `List`**: it covers all user objects.
  - All databases except `postgres`, `template0` and `template1`; a database that an owner turned into a template therefore stays visible.
  - Roles without a database, which an interrupted operation may have left behind.
  - An object is "managed" if it carries the `loch-managed` comment; the name alone is no longer enough.
  - Truncated output is an error.
- **PG deletion**: `NOLOGIN`, closing of sessions, `IS_TEMPLATE false`, `DROP DATABASE … WITH (FORCE)`, `DROP OWNED` (revokes the privileges granted by other tenants), then `DROP ROLE`. Each step is idempotent.
- **PG creation**:
  - the database is created with `ALLOW_CONNECTIONS false`, then `REVOKE`, then opened;
  - connections: `CONNECTION LIMIT 20` per role, `max_connections=200` on the instance;
  - password rotation closes open sessions.
- **`Init`** is idempotent and runs before each creation, not only at instance creation.
- **Container verification**: in addition to the name, the image and the labels, it checks:
  - the command;
  - the exact set of mounts (data, secret, generated files);
  - the absence of privileged mode, published ports, host network, PID or IPC, and added capabilities.
- **`Retire`** can resume an interrupted retirement: it restarts the instance to re-read its catalog.
- **Rollback**:
  - bounded to 2 min;
  - it never archives;
  - it invalidates the container cache;
  - right before `up`, the files are checked to be intact.
- **`modified` instance**: its retirement stays blocked. Creation, listing and rotation remain possible, however, because the container is verified strictly.
- **Compose**: `stop_grace_period: 60s` added.
- **Contract**: `ValidateName(v Version, name)` receives the version, for the 16-character limit of MySQL 5.6. Generated files are validated at startup, in the registry.

Still to do:
- **Step 5**:
  - inject the compose semaphore shared with hosting (`Config.ComposeSlots`);
  - validate the configuration (absolute, distinct paths);
  - set `Cache-Control: no-store` and a `recover` in the handler.

## 13. Remaining risks

- Long synchronous creation: if the connection drops, the password is lost (it is reset). Reverse proxy timeouts in production must be checked.
- `DROP … WITH (FORCE)` cuts the sites' connections.
- Shared network: authentication is the only barrier between sites.
- No disk quota per database: a database can fill `/data/services`.
- End-of-support dates to maintain, as for PHP.
- MySQL 5.6: end of life, no security updates; emulated (slow) on arm64.
- MySQL 8.4: plaintext password sent to the engine (stdin) as long as the `caching_sha2` hash is not computed in Go.
- In-memory lock: it assumes a single API instance.


## 14. Implementation review (2026-11-04)

Engines delivered: PostgreSQL 15–18, MariaDB 10.11/11.4/11.8, MySQL 8.4/5.6, MongoDB 6.0/7.0/8.0 (added on request, without TLS for now). All validated on real images (`make test-integration`).

Deviations from the plan:
- **MySQL/MariaDB TLS**: server-side `require_secure_transport` (the "simple" option of Q-TLS) rather than per-account TLS; MySQL 5.6 cannot enforce TLS and, like any version out of support, can only be published on loopback.
- **Exposure**: rendered in `compose.override.yaml` with a `pub` network specific to the instance; the applied exposure is recorded in the override and the container is verified against it.
- **Fail-closed**: a hand-edited `compose.yaml` is never run by the panel; a failure to close or restrict a port stops the instance instead of reopening the old port.
- **Compose service** renamed `svc` (neutral for future engines).

### Residual risks (final security review)

- **CSRF**: fixed globally (`SameOrigin` middleware on all writes, normalized WebSocket origin). Still possible: a logout CSRF (logout is a GET, minor impact), and hardening with `SameSite=Lax` on the cookie if the front end and the API share the same site.
- Shared `loch-services` network: an attached site reaches all instances; a host container can join the network and spoof an alias (internal instances have no TLS). Isolation relies on authentication.
- No memory/CPU limit and no disk quota per instance or per database (a tenant can saturate the instance or `/data/services`); pre-authentication DoS possible on a published port: the `DOCKER-USER` rule is a prerequisite for public publishing.
- The credentials given to a hosted site end up in plaintext in its environment variables (the site's `compose.yaml`): plan secrets support on the hosting side.
- TLS fingerprint read from disk (directory writable by the CI); images on mutable tags, without digest pinning.
- No backup or trash: every deletion is permanent (`SERVICES_ARCHIVE_ON_RETIRE` only covers instance retirement).
- A restricted profile given access to a `svc-*` container (exec, cp) reaches `/run/secrets/admin_password`.

### Preparing RabbitMQ and NATS (architecture review)

To do in the core before adding these engines:
1. **Multiple ports**: `Engine.Ports() []PortSpec{Name, Container, Role, Exposable}` instead of `DefaultPort()`; exposure, override, `portsMatch` and `ConnectionInfo` per port (AMQP 5672/5671, management 15672 not exposable; NATS 4222, monitoring 8222 bound to 127.0.0.1).
2. **`ConnectionInfo(ConnParams{Host, Name, Password, Ports, TLS})`** to produce `amqps://`, `tls://`, the management URL; new keys (`vhost`, `account`).
3. **File-managed resources (NATS)**: `ServiceSpec.DynamicDirs` (mounted directory, content owned by the provisioner) and `Target.Files` (atomic `FileStore` under lock); `isModified`/`filesIntact` only compare their existence. Reload with `nats-server -t` then `SIGHUP`, bcrypt hash computed on the panel side.
4. **`KindMessaging`** and a resource label per engine; frontend: menu and routes built from `GET /services/config` (one group per `kind`, route `/services/:engine`, namespace `services`); CLI/MCP: `services_resources` / `services_create_resource` tools, extensible allowlist of public keys.
5. **RabbitMQ**: `RABBITMQ_NODENAME=rabbit@localhost`, `loopback_users.admin = true`, removal of `guest` in `Init`, provisioning in a single call (`rabbitmqctl import_definitions` with `password_hash` computed on the panel side), `loch-managed` tag, exhaustive `List` excluding the `/` vhost.

## 15. Cache and messaging: Redis, Valkey, NATS, RabbitMQ (2026-11-04)

### Topology, based on the measured footprint (idle, official images)

| Engine | Memory | Processes | Image | Native multi-tenancy | Choice |
|---|---|---|---|---|---|
| Redis 8.4 | 12 MB | 6 | 132 MB | weak (one database, global commands, shared `maxmemory`) | **dedicated**: one container per resource |
| Valkey 9.0 | 18 MB | 7 | 65 MB | same | **dedicated** |
| NATS 2.12 | 11 MB | 10 | 39 MB | accounts (file config + reload) | **dedicated** (JetStream isolation, no shared config) |
| RabbitMQ 4.2 | 184 MB | 57 | 405 MB | vhosts + permissions + limits | **shared**: one instance per version, one vhost per resource |

Rule: shared instance when the engine is heavy and isolates its tenants natively (databases, RabbitMQ); dedicated instance when it is light and its internal isolation is weak (Redis, Valkey) or costly to administer (NATS). A dedicated instance is a standalone named resource (`svc-redis-<name>`), joined by the sites through the `loch-services` network; it has a size chosen at creation (container memory and CPU limit).

### Core ("dedicated" mode)

- `Dedicated` `Lifecycle`: the instance is the resource. `InstanceRef.Name`; key `<engine>-<name>` (versions start with a digit, names with a letter: no collision with `<engine>-<version>`). Version and options read from `x-loch` and validated against the catalog.
- Enumerated options declared by the engine (`Options()`), chosen at creation, recorded in `x-loch` and rendered in the compose file; `Service(ref, v, opts)`.
- `ServiceSpec`: `User`, `MemLimit`, `CPUs`, `NoAdminSecret`, `State` (`state/` directory mounted read-only on `/etc/loch/state`, written by the panel: password hashes). Container verification extended (memory, CPU, user, `state` mount).
- No administration account in Redis/Valkey/NATS: the panel runs nothing inside them. Creation = write the compose file and the state, start; rotation = rewrite the state then restart (all connections dropped); deletion = retirement of the instance.
- `SERVICES_MAX_DEDICATED_INSTANCES` (default 20 per engine) caps the number of containers.
- `ConnectionInfo(ConnParams{Host, Port, Name, Password, TLS})`: `rediss://`, `amqps://`, `tls://` schemes when TLS is required.

### Security per engine

- **Redis/Valkey**: `default` disabled; tenant `+@all -@admin -migrate` on `~* &*` (no `CONFIG`, `REPLICAOF`, `MIGRATE`: file writes and SSRF; no `ACL`, `MODULE`, `DEBUG`, `SHUTDOWN`); `enable-debug-command no`, `enable-module-command no`, `enable-protected-configs no`; `healthcheck` user limited to `PING`, on a unix socket; SHA-256 hashes in the ACL file; chosen `maxmemory` + eviction policy + persistence; TLS on the same port (`port 0`) when exposed.
- **NATS**: own configuration (the default image opens monitoring and a cluster with hard-coded credentials); non-root user (1000); monitoring on 127.0.0.1; no cluster, gateway or leafnode; one user, bcrypt password; bounded JetStream (memory, disk); `max_connections`, `max_payload`.
- **RabbitMQ**: plugins disabled (the image enables Prometheus, port 15692 without authentication); Erlang distribution and epmd on loopback (`inet_dist_use_interface`, `ERL_EPMD_ADDRESS`); `guest` and the `/` vhost removed; resource = `loch-managed` vhost + user of the same name (permissions on its own vhost only, `loch-managed` tag); per-vhost limits (connections, queues); password on stdin (`rabbitmqctl` without `-q`, which blocks otherwise); rotation + closing of connections; TLS by replacing `rabbitmq.conf` (`listeners.tcp = none`).

### Interface

Menu by category: Databases (MySQL, MariaDB, PostgreSQL, MongoDB), Cache (Redis, Valkey), Messaging (RabbitMQ, NATS). Routes `/services/:engine` and `/services/:engine/new`: full-page creation in the Scaleway style (numbered sections as cards: version, size and options, name; sticky summary on the right), credentials shown only once.

- Race window between the file check and the execution of `docker compose` (TOCTOU): reduce it by passing the verified bytes to compose.
- No disk quota per instance (Redis AOF, JetStream bounded by its own limit, RabbitMQ queues bounded by policy).
- Images on mutable tags, without digest pinning.

## 16. Object storage: Loch S3 (2026-11-05, planned)

Decisions (validated with the user):

- **Mode chosen by the configuration.** Without a Loch S3 admin key in the panel `.env`, the engine `s3` is **standalone**: one dedicated container per resource (`svc-s3-<name>`), the users file rendered by the panel with a single root user, mounted read-only, the admin API off. With a key (`SERVICES_S3_ADMIN_API_KEY`), the engine would be **shared** (`svc-s3-<version>`, a resource = a user + its bucket, administration via `docker exec` on a loopback-only admin listener, never through the shared network). One engine id, two Go types selected at startup.
- **Shared mode refused for now.** A security review of Loch S3 (2026-11-05) found a cross-tenant read (CopyObject source not authorized), cross-bucket deletions (path traversal through `uploadId` and `versionId`), and secrets in the logs (every request header logged); the admin API shares the tenant port. The Loch S3 team fixed the first three in its 1.3.0 work (not released yet); the pinned 1.2.0 image still has them, which only affects a tenant's own instance in standalone mode (the secret itself never travels, so it is never logged). Until a Loch S3 release with a separate admin listener, per-user limits and purge has been audited, setting the admin key disables the s3 engine only (error in the logs, the other engines keep working; the module is disabled with `SERVICES_MISCONFIGURED` only if s3 was the only enabled engine) instead of silently falling back. A `SERVICES_EXPOSED_PORTS` entry naming an s3 instance then disables the module (unknown instance).
- **Mode switch**: with the key set, a startup warning lists the `svc-s3-*` instances (they keep running but are no longer managed); documented procedure: switch back, delete, switch.
- **Secret at rest in clear**: SigV4 requires the server to know the secret, so no digest. The users file is 0400, owned by the container uid, in the 0700 private directory, never in an environment variable or in `compose.yaml`.
- **Region shown**: `us-east-1` (SDK default; any region is accepted). Path-style URLs.
- **Default bucket** at creation (`S3_INIT_BUCKETS`, Loch S3 1.3.0). SSE-S3 postponed (the key would sit on the same disk as the data).
- **Image**: `ghcr.io/loch-sh/s3:<version>`, an explicit exception to the mirror rule (our own image, not on Docker Hub).

Phase 0 results on `ghcr.io/loch-sh/s3:1.2.0`:

- Image uid:gid 100:101 (dynamic `adduser -S`); works with an arbitrary uid (10001), read-only root filesystem, `cap_drop: ALL`, `no-new-privileges`, users file 0400 in a read-only directory. Busybox `wget`, `nc` and `timeout` are available.
- Missing or invalid users file in a read-only directory: exit 1 (fail-closed). The file is never rewritten without the admin key. The startup log says "User management API: enabled" even without a key (calls do return 403).
- Idle memory under 1 MiB; 2 threads idle, 14 during a multipart transfer.
- Any region accepted; wrong secret: `SignatureDoesNotMatch`; anonymous: 403.
- aws-cli 2.31 (default checksums): create, put, multipart upload work. **Downloads are corrupted**: Range requests are ignored (a 10-byte range returns the whole object), and aws-cli downloads large objects in parallel ranges. Blocking; fix requested.
- AWS SDK for PHP 3.402: create, put, get, presigned GET, multipart: OK.
- Healthcheck possible on 1.2.0 without a secret (`GET /` answers 403), replaced by `/_loch/health` once released.
- With a Docker named volume, the image's `/data` (100:101) is copied into an empty volume; the panel uses bind mounts, which are not affected.

Switch to Loch S3 1.3.0 (2026-11-05): Range requests (parallel downloads no longer corrupted), `/_loch/health` used as the healthcheck, `S3_INIT_BUCKETS` (the resource bucket, returned as the `bucket` credential), quota (`S3_MAX_STORAGE_BYTES`), the panel runs the container as 10001:10001 (the image keeps 100:101 for its existing volumes; the panel owns its data directories, so it does not depend on the image user), `S3_MAX_BLOCKING_THREADS=32` (pids limit 128), a 16 MB `/tmp` tmpfs. The 1.2 entry was removed from the catalog (never released by the panel). Integration test on the 1.3.0 build: bucket created at start, 25 MB multipart upload and parallel ranged download identical, suffix range, health, rotation, resize, deletion.

Server-side encryption (2026-11-05): `encryption` option (off by default, fixed at creation). Generic core support: `ServiceSpec.GeneratedKeys` (random 32-byte keys created once in the state, 0400, kept for the instance life) and `OptionValidator` (an option refused on versions that would silently ignore it). Delivered by the Loch S3 team in 1.4.0 (`S3_ENCRYPTION_KEY_FILE`, `S3_ENCRYPT_BY_DEFAULT`); the catalog moved to 1.4. Integration test on the 1.4.0 build: object encrypted by default (AES256), read back identical, no plaintext in the data directory, key in neither `docker inspect` nor the logs, still readable after a rotation.

## 18. Private networks (2026-11-05)

### Context

Until now every site that asked for it joined one network, `loch-services`, shared with every instance: any connected site reached every instance, and authentication was the only isolation (decision D7). That was acceptable for engines with strong authentication; it is not for ElasticMQ (§17), which has none, and the residual risk of §14 (clear traffic and DNS alias hijacking on the shared network) grew with every engine. Exposing a port had also been left to the environment (D10), which forced an edit of `.env` and a restart for each database a customer wanted to reach from outside.

### Options considered

1. **A network vendor or overlay** (a CNI, a VPN mesh, Docker Swarm overlay networks). Rejected: a new dependency and a new failure mode, stacks that no longer boot with `docker compose up -d`, and a lock-in the product does not have anywhere else (compose is the source of truth for hosting and services).
2. **Per-pair networks created implicitly** (one per site and instance). Rejected: the number of networks explodes against the address pools of Docker, and nobody can reason about them.
3. **One network per tenant group, created by the admin, plain Docker** (retained). Admins name the networks and decide who joins; the panel renders, verifies and reports.
4. **Keep the shared network and filter with iptables.** Rejected: host-specific rules the panel cannot verify, and they would not survive a Docker restart reliably.

### Decisions

- **Native Docker only, no lock-in.** A network is a plain `internal` bridge network, labelled `sh.loch.managed=true` (and `sh.loch.network=<name>`), named `loch-net-<name>`. Compose files reference it as `external`, and each compose header lists the exact `docker network create --internal [--subnet ...] --label ... <docker name>` command, so a stack boots on a fresh host without the panel. The registry (`DATA_DIR/networks.json`: ID, subnet, labels) exists only for the panel's own verification and is never needed at runtime. Docker allocates the subnets (the admin configures `default-address-pools`; the defaults hold about 31 networks); a manual subnet is optional (private ranges, `/16` to `/28`, overlaps refused by Docker itself).
- **A network is not an access control against CI stacks or the Docker socket.** Any container can join a network by name. Accepted by design: the panel detects the members it does not manage, shows them (`unmanaged`) and lets an admin disconnect them. Containers on several networks bridge them only at the application level (no `NET_ADMIN`, no forwarding); sites on any panel network lose `NET_RAW`.
- **`services` becomes a system network.** `loch-services` (`SERVICES_NETWORK`) is registered as the system network `services`: it cannot be deleted, and is the default for new sites and for authenticated instances. Engines without authentication (ElasticMQ) are refused on it and must use a private network; they are never published beyond the loopback.
- **Membership lives with the member.** A site lists its networks in `x-loch.networks` of its compose file (`SpecVersion` 6, replacing `servicesNetwork`); an instance in its private reference `instance.json`, now written for shared instances too (`ManifestVersion` 2). Existing development instances are therefore "modified" and must be purged: no migration, the feature is not in production.
- **Attach and detach recreate the member.** Compose recreates a container whose networks change, and a manual `docker network disconnect` is undone by the next `up`. A detach disconnects first; if the instance then fails to restart, it is stopped and never reconnected. An instance keeps at least one network, otherwise Compose would give it a default network with Internet access (`SERVICE_LAST_NETWORK`).
- **Stricter verification.** The container must be on exactly the networks of its reference, by Docker ID equal to the registry's, with its alias on each; nil network settings are refused (they used to pass). The live network is checked too (ID, `internal`, local `bridge`, labels, no compose project label, subnet). At startup the reconcile recreates a missing network with the same subnet and reports a replaced one as compromised: its members are not trusted. The panel never adopts a Docker network by name.
- **Exposure moves from `.env` to the panel**, which reverses D10 ("the web interface allows no change"). It is chosen per instance (scope `services:expose`, not implied by `services:write`, no MCP tool), recorded in the private reference and applied by the existing fail-closed path (§6bis). It is bounded by a policy only the environment can set: `SERVICES_EXPOSE_ALLOWED_CIDRS` (host bind addresses: Docker cannot filter client sources, that is `DOCKER-USER`'s job), `SERVICES_ALLOW_PUBLIC_BIND`, `SERVICES_TLS`, `SERVICES_ALLOW_TLS_OPTIONAL` (replacing `SERVICES_TLS_OPTIONAL`) and reserved ports. `0.0.0.0` only if listed alone; loopback only for out-of-support versions, unauthenticated engines and engines that cannot require TLS. Removed: `SERVICES_EXPOSED_PORTS`, `SERVICES_PUBLISH_ADDRESS`, `SERVICES_TLS_OPTIONAL`.
- **Environment linter** (`internal/env`). Every variable is read through a `Reader` that records every problem. Unknown variables with a known prefix (typos, with a suggestion) and removed variables stop the API, values are never printed. Configuration errors, including invalid `SERVICES_ENGINES` / versions and the TLS certificate files, now stop the API instead of disabling the services module; installation checks (preflight, Docker) still only disable the module.
- **`TRUSTED_PROXIES`** replaces the hard-coded trust of `172.16.0.0/12` for `X-Forwarded-For`: a container could forge its IP for the rate limit and the audit trail. Default: loopback only. `loch proxy` now picks the networks of a target in name order (deterministic).

### Consequences

- Sites and instances are isolated by default only if admins create and use private networks: the default network `services` keeps the behaviour of D7 for authenticated engines, with its limits (§14 residual risks).
- Changing the networks of a member costs a container recreation (a few seconds), documented in the interface and the CLI.
- A published port can now be opened by an admin session or an API key holding `services:expose`: the blast radius is the environment policy, which defaults to the loopback.
- The registry and the references are two sources to keep consistent; verification treats any divergence as untrusted rather than repairing it.
- Existing development instances, and any `.env` using a removed variable, must be migrated by hand.

Documentation: [Private networks](../networks.md), [Managed services](../services.md#networks-of-an-instance), [Managed services security](../services-security.md#networks-and-exposure).

## 19. Version discovery and updates of dedicated instances (2026-11-05)

### Context

Versions were a fixed list per engine in the code, filtered by `SERVICES_<ENGINE>_VERSIONS`. Every new release of an engine needed a panel release, versions that went out of support stayed on offer, and an existing instance could never be moved to a newer image: tags are mutable and `--pull missing` never refreshes an image already present (§14 residual risks), so fixes of the engines were not applied. Dedicated instances (§15) are light and hold one tenant, which makes an in-place update realistic; shared instances serve several sites, and a version change there is a migration.

### Decisions (validated by the product owner on 2026-11-05)

- **Dynamic catalog for all engines.** Tags are listed on the **origin** registry (Docker Hub anonymously, `ghcr.io` for Loch S3: `mirror.gcr.io` cannot list tags). Each candidate image is checked (manifest `HEAD`, which gives the digest) on the registry it is **pulled from**, the mirror, so that nothing is offered that cannot be pulled. Support dates come from endoflife.date: `eoasFrom` (end of active support) becomes `activeSupportUntil`, `eolFrom` (end of security support) becomes `supportUntil` and drives `deprecated`. Engines not listed there (NATS, Mosquitto, ElasticMQ, Loch S3) are supported as long as they are published.
- **Engine contract.** Each engine declares `Releases()` (`Source`, `Tag` regular expression with an optional patch group for the exact-tag engines Mosquitto, ElasticMQ and Loch S3, `LineTag` format, `EOL` product, `Min` version) and `VersionOf(version, tag)`. `Catalog()` becomes the built-in fallback used until a discovery succeeds. An engine declares only a minimum: it does not say which majors it was tested with.
- **What is offered.** At creation: the latest supported and available version of the **3 latest majors** (the major is the first number), plus the versions pinned with `SERVICES_<ENGINE>_PINNED_VERSIONS`, always offered even out of support (MySQL 5.6 only when pinned). `SERVICES_<ENGINE>_VERSIONS` is removed, and the API refuses to start with a hint. `SERVICES_UPDATE_CHECK_INTERVAL` (hours, default 12, 0 = on demand only). The result is cached in `DATA_DIR/services-catalog.json` and sanitized when loaded. Outbound HTTPS is needed to `registry-1.docker.io`, `auth.docker.io`, `ghcr.io`, `mirror.gcr.io` and `endoflife.date`.
- **Existing instances stay managed whatever their version** (any version from the engine's minimum): a shared instance of a version that is no longer offered keeps accepting resources. The offer only concerns creation.
- **Updates of dedicated instances, in one click.** Redis, Valkey, NATS, Loch S3, ElasticMQ and Mosquitto can move to a newer image of their version (new digest of a floating tag, or newer patch tag) or to one of at most 3 newer supported versions. Never a downgrade, neither of version nor of patch. Shared instances are not updated (`SERVICE_UPDATE_NOT_SUPPORTED`).
- **The image is part of the private reference.** `instance.json` records the `image` an instance runs (migrated at startup by `RecordImages`). The instance is verified, and its files rendered, against that image, which must be one the engine computes for a tag of the version.
- **Update flow.** The digest is read on the mirror, the image is pulled **by digest** (content-addressed, 4 minutes at most), then under the instance lock the container is verified, the pulled image is tagged with the tag of the version (replaced by pinning by digest, see "Review fixes" below), and `applyConfig` (shared with the option changes of §15) rewrites reference, state, compose and override files and runs `up --force-recreate` (5 minutes at most). On any failure the files **and the image tags** are restored and the instance restarted on its previous image. Audit `service instance updated` / `service instance update rolled back`. The CLI long timeout goes from 6 to 10 minutes.
- **No data backup before a version change.** The panel has no backup (§14): the operator is responsible, and it is documented.
- **MySQL 9 and later** have no `mysql_native_password`: legacy authentication is only offered on MySQL 8.4 to 8.x.
- **API.** `GET /services/config` gains `catalog {checkedAt, failed[], throttled}`, versions gain `activeSupportUntil` and `pinned`; instances gain `supportUntil`, `activeSupportUntil` and `update {image, latestImage, versions[]}`; `POST /services/instances/{instance}/update` `{version?}` returns `{updated, version, image}`; `POST /services/updates/check` (throttled to 30 seconds), both with scope `services:write`. New codes `SERVICE_UPDATE_NOT_SUPPORTED` 400, `SERVICE_VERSION_DOWNGRADE` 400, `SERVICE_IMAGE_PULL_FAILED` 502, `SERVICE_RELEASES_UNAVAILABLE` 503. CLI `loch services updates [--check]` and `loch services upgrade <instance> [--version] [--yes]`, MCP `services_upgrade_instance` (image of the current version only: a version change is irreversible, left to a human, like publishing a port).
- **Second security review.** Every failure of the update, including those before a file is written, gives the tags back; after the restart, the container must run the image pulled by digest (else it is rolled back, and a tag moved by someone else meanwhile is never moved back); the moves of one tag are serialized; registry redirects only to the same host or known registry hosts; web routing links in the containers page only for valid host names (labels are set by any container). Not done: a highest tested version per engine (new majors stay offered by design, see above) and a cross-check of the mirror digest with the origin registry.

### Security

Registry and endoflife.date answers are untrusted: strict tag regular expressions (images are only built by engine code), size caps (8 MiB per response, 50,000 tags, 20 pages), at most 24 digest checks per engine and discovery, a token realm restricted to the registry host, `auth.docker.io` or `ghcr.io`, HTTPS-only redirects, dates and digests validated, the cached file validated again when loaded. A failed discovery keeps the previous values. A tampered image in the reference makes the instance modified (never run). Details: [Managed services security](../services-security.md#version-discovery-and-updates).

### Consequences

- Fixes and new releases of the engines reach new and existing dedicated instances without a panel release, at the cost of an outbound dependency (a failure falls back to the built-in or previous catalog).
- An update restarts the instance (a few seconds) and changes its image: the operator accepts the version risk.
- `applyConfig` is the one path that rewrites a dedicated instance, shared by option changes and updates.

### Residual risks

- **The mirror is trusted** for the content of the images: the digest is read on it and verified after the pull, but a compromised mirror is consistent with itself.
- **No data snapshot** before a version upgrade: a newer version may convert the data on first start, and going back is refused.
- **New majors are offered untested by design**: engines only declare a minimum, so a major that changes behaviour can be offered before the engine code is adapted.
- **Shared instances stay on their version**: moving them is a manual migration.

Documentation: [Managed services](../services.md#versions-and-updates), [Managed services security](../services-security.md#version-discovery-and-updates), [API](../api.md#managed-services).

### Review fixes (2026-11-05)

A review of the merged feature found that moving the local tag broke the isolation between dedicated instances: the instances of a version share its tag, so updating one of them changed what the others ran at their next recreation (options, published port, networks), unaudited, and a rolled-back update could give the tag back to the old image and bring an already updated instance back to it. A version change rolled back the old tag without the "unchanged since" check nor its lock. The tag flow above (tag after verification, give back on failure, one move per tag at a time) is replaced:

- **Images pinned by digest.** The compose file of a dedicated instance runs `repo:tag@sha256:…` and `instance.json` records the `digest` next to `image`; an update renders the new digest and never moves a tag (`TagImage`, `lockTag` and the restore hook of `applyConfig` are removed). A rollback restores the files, hence the previous pinned reference. The container verification accepts a container created from the pinned reference or, before the pinning, from the tag alone, but in both cases the image it runs (by content ID) must carry the pinned digest for the repository of the tag. The `x-loch` manifest does not carry the image: `ManifestVersion` is unchanged.
- **Digest at creation: from Docker, not from the registry API.** The tag is pulled when absent (as compose would), and the digest is one Docker recorded for the repository of the tag in the image's `RepoDigests` (the mirror's digest of the tag when the catalog knows it and the image carries it, otherwise the smallest). Resolving it on the mirror like an update would add a dependency on the registry API and its token endpoint (and on `Releases` being configured) to every creation, and could pin a newer image than the one already cached; the `RepoDigests` digest is what Docker verified when it pulled, and the same derivation serves the migration. An image without such a digest (built or loaded locally) is run by its tag, logged.
- **Migration (`PinImages`, at startup after `RecordImages`).** An instance without a digest is pinned to the image its **verified** container runs (`RepoDigests` for the repository of its tag, never a digest from a file of the stacks directory); the reference is written first, then `compose.yaml`; the container is not recreated. When no digest can be derived, the instance keeps its tag-only rendering, logged, and is pinned by its next update.
- **A compose file without its digest is never run.** The rendering without the digest while the reference has one (an interrupted migration, an update of an unpinned instance interrupted between its reference and compose writes, or CI writing it back at any time) would recreate the container from the shared tag. The instance is then reported **modified**, so no operation runs compose on it (exposure, options, networks, update, startup application of the exposures); only `PinImages` repairs it at the next start, and only with a digest the verified container's image carries: the recorded one, or else (interrupted update) the running image's, the container being verified against the tag-only rendering, with a warning logged. After a panel crash, the next start repairs it before anyone sees it; a compose file written back by CI leaves the instance modified until the next start of the panel. If the compose file cannot be written, the pinning writes the previous reference back and reports the error (an update returns it). An interrupted update of an already pinned instance (compose file pinned to the previous digest) is not repaired: it stays modified.
- **Shared instances keep their line tag.** One instance per engine and version, never updated by the panel, no engine image shared with a dedicated engine, and no panel operation moves a tag any more: no other instance can be affected. Pinning them would need the same migration for every database instance for no isolation gain; to reconsider if shared instances ever get updates.
- **Several digests for one image**: Docker may record more than one digest of an image for its repository, each naming that image. An update is offered only when the running image does not carry the mirror digest; the verification accepts a container created from any digest the image carries, provided it also carries the pinned one.
- **Accepted residual windows.** A crash of the panel between the reference and the compose write of an update of a pinned instance leaves a compose file with the previous digest: the instance is reported modified, as for an option or version change interrupted the same way (pre-existing `applyConfig` window). A new instance uses the image already cached for its tag (as compose did): it may start on an older image of the version and offer an update immediately.
- **Options validated again under the lock** for the target version (they may change between the first check and the lock).
- **A tag list cut by the 20-page cap is an error** (the engine is listed in `catalog.failed`) instead of a silently truncated list.
- Interface: a version change is never preselected in the update dialog (only the image update of the current version is); `SERVICE_RELEASES_UNAVAILABLE` is translated.

## 20. Functions and S3 event notifications (2026-11-05, planned)

### Context

Target use case: a user uploads an image to a Loch S3 bucket, the bucket emits an event, a function resizes the image and stores the result in another bucket. This is the AWS pattern S3 → notification → Lambda → S3. Two pieces are missing: Loch S3 has no bucket notifications (nothing in `loch/s3/src`), and the panel cannot run functions.

### Options considered

- **Nuclio as an engine.** Rejected. Without Kubernetes, Nuclio runs as a "local platform": its dashboard builds one image per function and starts one container per function, so it needs the Docker socket mounted. That breaks every guarantee of the module: the strict container verification refuses the socket mount (`manager_test.go`), `cap_drop: ALL` / `read_only` / non-root are impossible, the function containers are created outside any compose file and outside `instance.json`, the infrastructure no longer boots from compose alone, the local dashboard has no authentication, and the images are on `quay.io` (a new exception to the mirror rule). Whoever reaches the dashboard can start a container with the socket, which is root on the host, panel and audit trail included. Nuclio also presents its Docker mode as meant for development.
- **Nuclio as a hosted site** (admin only, warning "root-equivalent access to the host"). Possible for trusted internal use only; not a product offer.
- **A container-based FaaS that needs no socket** (faasd, Spin, wasmCloud). faasd drives containerd, which is the same problem; WASM runtimes would have to be checked against `read_only` and non-root, and they impose their own SDK.
- **Functions built on the panel's own model** (chosen): one panel-rendered compose per function, with the same constraints as the dedicated instances, in a module of its own (below).

### Decisions (validated by the product owner on 2026-11-05)

- **No vendor lock-in is the main principle**, at every layer; each layer must be replaceable on its own:
  - *Runtime*: a function is a compose stack under `HOSTING_STACKS_DIRECTORY/fn-*/`, startable with `docker compose up` without the panel. The panel renders and applies it, as for `svc-*`.
  - *Code*: a handler written for AWS Lambda (`exports.handler = async (event) => …`), no loch SDK, no loch-specific signature: the same code runs unchanged on AWS Lambda.
  - *Events*: AWS formats only (see below), so a function receiving Loch S3 events also receives MinIO's, and the other way round.
  - *Secrets*: the code reads environment variables; the secret store behind them can change without touching the code.
- **A module of its own (`internal/functions`), not a `services` Kind.** `services.Engine` assumes a catalog image whose whole configuration is computed by the engine; a function carries client code and, later, HTTP routes, which makes it closer to a hosted site. It reuses `composekit` (runner, atomic files, preflight), the Traefik label rendering of `hosting` (to extract), `networks` (new member kind `function`), `releases` and the update flow of §19 for the runtime images, and the verification principle of `services` (private reference `function.json`, compose identical to what the panel renders).
- **Runtimes in v1: the AWS Lambda base images published by AWS** (`amazon/aws-lambda-nodejs`, `amazon/aws-lambda-python`, Apache-2.0, through `mirror.gcr.io`), versions discovered by `releases`. Invocations go over HTTP (`POST /2015-03-31/functions/function/invocations` on port 8080), served by loch's own Lambda Runtime API, not by the bundled Runtime Interface Emulator (see "Decision after the spike"). The code is a zip (handler and dependencies) uploaded, validated (zip-slip, no symlinks, size and file-count caps) and extracted into a versioned directory mounted read-only at `/var/task`. Every upload is a deployment; the last 3 are kept for an instant rollback. Never a build on the server.
- **Client-provided images: later.** Any image implementing the Lambda invocation API would be accepted, from registries the admin allows, pulled by digest; postponed to avoid an allowlist of registries in v1.
- **Hardening**, as for the dedicated instances: `cap_drop: ALL`, `read_only`, non-root, `no-new-privileges`, `/tmp` tmpfs, memory / CPU / PIDs limits, no Docker socket, image pulled by digest and recorded in the reference.
- **Secrets: native to the panel in v1.** Stored in `.loch/fn-<name>/secrets/` (0400, private directory, never in `compose.yaml`), entered once and never shown again, exposed to the function as environment variables (the Lambda contract). The environment of `fn-*` containers is masked in `GET /docker/{id}` and in the containers views, so that a container read scope does not reveal them (Docker socket holders are root anyway). **Infisical later**, as an optional source: a variable may reference `infisical://<project>/<env>/<path>/KEY`, resolved by the panel at deployment with one read-only machine identity (generic `SECRETS_INFISICAL_*`, reusable for hosted sites), never by the function: removing Infisical leaves plain panel secrets. A changed value is applied at the next deployment or with a "resync secrets" action.
- **Triggers in v1:** manual invocation (panel, CLI, MCP) through `NetworkBridge` like `loch proxy` (the function is never published); a new cron job type `function_invoke`; members of its private networks (`http://fn-<name>:8080/…`), which is how the Loch S3 webhook will reach it. **Public HTTP: later**, through Traefik with an API Gateway v2 event translation.
- **Interface:** the existing "Serverless" menu group gets a "Functions" entry next to Cron: list `/functions`, full-page creation `/functions/new` (numbered cards: runtime and version, code and handler, resources, variables and secrets, networks, name; sticky summary), detail `/functions/:name` with the tabs Overview, Code (deployments, rollback), Test (JSON event, result, duration, logs), Logs, Configuration, Networks, Triggers.
- **API** (scopes `functions:read`, `functions:write`, `functions:invoke`): `GET /functions/config`, `GET|POST /functions`, `GET|PATCH|DELETE /functions/{name}`, `POST /functions/{name}/code`, `GET /functions/{name}/deployments`, `POST /functions/{name}/deployments/{id}/activate`, `POST /functions/{name}/invoke`, `POST /functions/{name}/{start|stop|restart}`, `PUT /functions/{name}/networks`, `POST /functions/{name}/update`. CLI `loch functions` (alias `fn`), MCP `functions_list|get|invoke|deploy` (no deletion).
- **Loch S3 bucket notifications** (Loch S3 team, 1.5, after the functions module):
  - AWS API `PutBucketNotificationConfiguration` / `GetBucketNotificationConfiguration`, events `s3:ObjectCreated:*` and `s3:ObjectRemoved:*`, prefix and suffix filters. Configured by the client with `aws s3api` or an SDK; the panel has nothing to manage.
  - AWS event JSON (`Records[].s3.bucket.name`, `object.key`, …).
  - Webhook target, which the AWS API lacks (it only knows SNS, SQS and Lambda): MinIO's convention (`arn:minio:sqs::<id>:webhook`), the endpoint and its secret set in the instance configuration.
  - Reliable delivery: a persistent outbox in the data volume, retries with backoff, so an event sent while the function restarts is not lost.
  - Requests signed with HMAC in a header, so a function can refuse calls that do not come from its S3 instance.
- **Loops**: a function that writes into the bucket that triggers it calls itself forever. Documented rule: write into another bucket or under a prefix outside the filter. Optional safeguard in Loch S3: a write carrying `x-loch-origin` of a notification rule never triggers that rule again.

### Phases

0. **Spike**: Lambda base images on `mirror.gcr.io`, Runtime Interface Emulator under the hardening above, startup time, concurrency, memory of an image resize with `sharp`.
1. **API**: model, rendering and verification, zip, deployments and rollback, invocation, networks, secrets and masking, audit, environment, documentation, unit and integration tests.
2. **Interface**: menu, pages, i18n in the 10 languages, mocks, Vitest and Playwright.
3. **CLI and MCP.**
4. **Cron `function_invoke`** and runtime updates.
5. **Later**: Loch S3 1.5 notifications as a trigger, public HTTP, client-provided images, Infisical, other notification targets (SQS through ElasticMQ, NATS).

### Phase 0 results (spike, 2026-11-05)

Run on Docker 29.9.2, arm64, with `amazon/aws-lambda-nodejs` and `amazon/aws-lambda-python` through `mirror.gcr.io`.

- **Hardening: no relaxation needed.** `read_only`, uid 10001, `cap_drop: ALL`, `no-new-privileges`, `/tmp` tmpfs, memory / CPU / PIDs limits, code mounted read-only at `/var/task` (world-readable), internal network, no published port: Node 22 and Python 3.13 work. Image user root, entrypoint `/lambda-entrypoint.sh`, the handler as the only argument; nothing written outside `/tmp`, no `HOME` needed. `LD_LIBRARY_PATH` includes `/var/task` (normal for Lambda, to allow in the environment check).
- **Required environment:** `AWS_LAMBDA_FUNCTION_MEMORY_SIZE` equal to the memory limit (otherwise Node is sized for 3008 MB and the kernel kills it instead of a clean heap error) and `AWS_LAMBDA_FUNCTION_TIMEOUT` (default 300 s).
- **Numbers:** cold start about 200 ms, warm invocation about 1 ms. `sharp` resizing a 4000×3000 JPEG to 800 px peaks at 49–77 MB (PNG 91–113 MB): 256 MB is enough, no OOM in any tested case.
- **Tags:** the plain tags (`22`, `latest`, `3.13`) are frozen since 2025-01-14 and amd64 only. Live builds carry an architecture suffix (`22-arm64`, `22-x86_64`) and dated tags (`24.2026.11.05.18-arm64`), rebuilt several times a day, without a multi-arch manifest list. `mirror.gcr.io` serves them with the Docker Hub digests, but answers `not found` or 429 on the first request of a tag: pulls by digest need retries. `releases` maps the host architecture to the suffix and uses the dated tags (patch group), otherwise every check would find a new image.
- **Errors:** a timeout and an exception both answer 200, a process exit 502; bodies over 6 MiB are cut silently. The result must be classified by the runtime, not by the HTTP status.
- **Concurrency: the Runtime Interface Emulator crashes** on two overlapping invocations (Go panic, container exit, every in-flight request lost), upstream v1.35 included. Any member of the function's networks could trigger it.
- **Sizes and licenses:** 617 MB (Node) and 820 MB (Python) uncompressed, shared per runtime; `THIRD-PARTY-LICENSES.txt` in the image, upstream repositories Apache-2.0.

### Decision after the spike (validated by the product owner on 2026-11-05)

- **The RIE is not used. Loch ships its own implementation of the Lambda Runtime API** (the public protocol documented by AWS), started through `AWS_LAMBDA_RUNTIME_API`, a branch the AWS entrypoint already supports. It owns the invocation endpoint on port 8080 and talks to the AWS `bootstrap` on loopback: a real queue (429 when full), per-invocation timeout, reliable error status (`X-Amz-Function-Error`), body size limit with an explicit error, and a health endpoint that does not invoke the function. The client code stays a standard Lambda handler and the AWS image is unchanged: no lock-in, at the cost of one loch component to maintain (open source, Apache-2.0). Rejected: a serializing proxy in front of the RIE (keeps a testing tool with a known crash and unreliable statuses), and `restart: unless-stopped` with one call at a time (any network member can still crash the function).
- How the component is delivered (a binary mounted read-only from the panel, or a small image layered on the AWS one) is decided at the start of phase 1.

### Plan reviews (2026-11-06)

Two reviews of the plan and of the runtime specification (security, AWS compatibility). The runtime part is in the `loch/lambda-runtime` specification (draft 3); the panel part amends the decisions above:

- **Invocations are authenticated** (reverses "no authentication" for network callers). Private networks are not an access control, and a forged S3 event would make the function use its own credentials on another object (confused deputy). The runtime requires a bearer token or SigV4 with a static key pair; the panel generates them per function (`.loch/fn-<name>/`, 0400, shown once, rotatable). Loch S3 1.5 signs its webhook body as well (HMAC, timestamp, replay window), not as an option.
- **The panel invokes through `docker exec … /loch/lambda-runtime invoke`**, never through `NetworkBridge`: the panel container never joins a tenant network (no exposure of the panel API to functions, no DNS impostor through `--network-alias`, no long-held bridge). The result is a fixed JSON envelope, always `application/json` + `nosniff`, payload and logs bounded and rendered as text only, no function header or content type ever copied (stored XSS on the panel origin otherwise). CLI and MCP present results as untrusted data.
- **Networks**: a function gets a dedicated network (`fn-<name>`) by default, never `services`; callers are attached explicitly. Outbound Internet is an explicit per-function option (off by default, audited, warning in the interface: it reaches the host gateway, the LAN and metadata endpoints unless `DOCKER-USER` rules say otherwise).
- **Runtime binary trust**: the trust root is the panel build (embedded table of runtime version, architecture and sha256, plus the public key of the signed releases), never a bare `SHA256SUMS`. Download over HTTPS from allowed hosts with the `releases` redirect rules and a size cap, hashed from the opened file, written under a temporary name then renamed, 0555 in a panel-owned directory, versioned directories never modified in place, architecture checked against the image. Re-hashed and compared with `function.json` before every `up`; verification requires the mount source to be the panel-computed path (bind, read-only, `rprivate`) and the entrypoint `["/loch/lambda-runtime"]`. `FUNCTIONS_DATA_DIRECTORY` must be outside `HOSTING_STACKS_DIRECTORY` (checked by the environment lint), `.runtime` and `.loch/fn-*` 0700.
- **Zip validation**: streamed to a temporary file (never memory) under `MaxBytesReader` (50 MiB), bounded concurrent uploads, disk quota and free-space preflight; extraction through `os.Root` into a temporary directory renamed atomically; every name validated (UTF-8, no NUL/control character, no `\`, no leading `/`, no `.`/`..`/empty component, ≤ 255 bytes per component, ≤ 4096 in total, depth ≤ 64, no duplicate after cleaning, no file that is also a directory prefix); regular files, directories and relative symlinks staying inside the tree only (needed by `node_modules/.bin`, created last, never written through, every parent `lstat`-checked); Store and Deflate only, no encryption; limits on bytes actually written (250 MiB in total and per file, 50,000 files, ratio ≤ 100:1, extraction timeout); modes normalized (0755 directories, 0644 or 0755 files: world-readable is mandatory for uid 10001; setuid/setgid/sticky stripped); a tree hash (sorted path, mode, sha256) and the zip sha256 recorded in `function.json`, checked before activate, rollback and start; the tree made read-only.
- **Secrets**: written to a 0400 `env_file` with `format: raw` in `.loch/fn-<name>/`, never in `compose.yaml`; values validated at entry (length, no NUL or newline); reserved names refused (`AWS_LAMBDA_*`, `_HANDLER`, `LAMBDA_*`, `LD_*`, `LOCH_RUNTIME_*`, the reserved `AWS_*` subset). Masking is central in the `docker` layer, not per handler: `GET /docker/{id}` returns `Config.Env` raw for every container today, so values are masked for functions (names kept) and the same is considered for hosted sites. Function containers are protected like the panel's own (`IsSelf`): shell, exec, cp, file tail, `loch proxy` and cron `docker_exec` refused (`FUNCTION_CONTAINER_PROTECTED`), and they cannot be granted in a restricted profile. Secret values never travel in MCP parameters nor CLI arguments (stdin or file only), `GET /functions/{name}` returns names only. At rest they are plaintext (compose must boot without the panel): documented, as are secret-bearing backups.
- **AWS SDK in functions**: `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` from panel secrets and `AWS_ENDPOINT_URL_S3` / `AWS_ENDPOINT_URL` for Loch S3, `AWS_EC2_METADATA_DISABLED=true` by default; S3 path-style addressing to check with Loch S3.
- **Hardening and verification** (on top of the dedicated instances): `security_opt` exactly `no-new-privileges:true` (default seccomp and AppArmor kept), `ipc: private`, no host namespaces, `ulimits` (`nofile`, `nproc`, `core: 0`), `shm_size`, `/tmp` tmpfs `nosuid,nodev` with a configurable size (default 512 MB like Lambda, counted against the memory limit), `/var/task` read-only, **`json-file` logging with rotation** (Docker's default never rotates: a logging loop fills the disk), `PYTHONDONTWRITEBYTECODE=1`, global quotas (number of functions, total memory and CPU). Verified: image digest, environment = image environment (its `LD_LIBRARY_PATH` with `/var/task` only if equal to the image's) + rendered variables + secrets by name, entrypoint and command (v1: AWS entrypoint only, handler matched by a strict pattern), mounts exactly runtime + active deployment + tmpfs + `env_file`, user 10001, networks, healthcheck, restart policy.
- **Cron `function_invoke`** needs `functions:invoke` (owner and API key) at creation, update and run; no overlap with the previous run, minimum period 1 minute, panel-side concurrency per function bounded; `LastOutput` keeps status, duration and size only, never the payload.
- **Scopes**: the module is admin only. `functions:invoke` is implied by neither read nor write; code and secrets need `functions:deploy`, `functions:write` covers configuration. The MCP invocation is opt-in per function; no MCP tool for secrets, deletion or purge.
- **Audit**: created / updated / deleted / purged, code deployed (zip sha256, size, file count), activated / rolled back, secret set or removed (name only), network attached or detached, egress toggled, runtime updated, verification refused; invocations aggregated per function and minute (never content) so that a cron or a script does not flood `audit.log`.
- **Deletion** removes containers, compose directory, every kept deployment, `.loch/fn-<name>/` (secrets, credentials, reference), upload leftovers and the dedicated network; purge with the typed name, as for instances.
- **Loch S3 1.5** (later): loop suppression (`x-loch-origin`) on by default, rate limit and circuit breaker per rule, bounded outbox (bytes, TTL, dead-letter log), batched or rate-limited bulk deletions; the webhook target is a panel-known function chosen in the instance configuration, reached by its verified container address, never by a name or a client-supplied URL.

### Phase 1, part 2 delivered (2026-11-06): deviations from the plan

- **Invoke credentials**: a runtime security review showed that every variable of the container is readable by the function code (same uid, `/proc/<pid>/environ` of `docker exec`'d processes). The panel shows the bearer token once and passes only its SHA-256 (`LOCH_RUNTIME_TOKEN_SHA256`); it keeps nothing else. SigV4 is off by default per function; when enabled, `LOCH_RUNTIME_ACCESS_KEY=<id>:<secret>` is in the container (readable by the code, it only lets the function invoke itself). Both go through a second 0400 raw `env_file` (`runtime.env`); there is no `state/` mount. Loopback calls (panel invocations, healthcheck) need no credential. Rotation: `POST /functions/{name}/credentials/rotate {sigv4?}`.
- **Image pinning** uses the architecture-suffixed line tag (`22-arm64`), not the dated tags: listing the tags of the AWS repositories would exceed the bounds of `releases` (rebuilt several times a day). Dated tags and updates come with the runtime updates (phase 4). Offered versions are built in.
- **Global budget**: `FUNCTIONS_MAX_TOTAL_MEMORY` and `FUNCTIONS_MAX_TOTAL_CPUS` (0 = the Docker host memory, 4 × its CPUs).
- **Stop** is recorded in the reference (`stopped`): configuration changes of a stopped function are written without starting it.
- **Kept deployments** are recorded in `function.json` (`kept`, with their tree hashes), so that an activation verifies the directory it mounts.
- **Invocation audit**: aggregated by the module; the global `api request` entry is skipped for successful (status < 400) `POST /functions/{name}/invoke` only.
- **Invocation lifetime**: `invoke --watch-stdin` (the runtime exits when its stdin closes; Docker closes an exec's stdin, never its stdout, when its client goes): the panel keeps stdin open and closes the exec connection when done or at its deadline. The event must be one JSON value (`INVALID_FUNCTION_EVENT`).
- **Review fixes** (2026-11-06): compose reads the checked bytes on stdin (`-f -`, no TOCTOU) and the project must hold exactly the function's container; uploads are paced (stall 15 s, 32 KiB/s after 30 s); variables, handler, networks and egress need `functions:deploy`; one container permission check for HTTP and WebSocket, `fn-*` permissions dropped; docker and stack actions refused on functions; lock order networks then function, network operation lock bounded.
- `POST /functions/{name}/update` (runtime update) is not in this part.

### Custom runtime (2026-11-06)

Go, Rust and any compiled language run on the OS-only AWS image `provided.al2023` (runtime `provided`, Docker Hub `amazon/aws-lambda-provided`, line tags `al2023-arm64` / `al2023-x86_64` on `mirror.gcr.io`), with the same entrypoint and command as the other runtimes (`-- /lambda-entrypoint.sh <handler>`): the image script needs exactly one non-empty argument, exports it as `_HANDLER` and runs `/var/task/bootstrap`. The handler is therefore optional and defaults to `bootstrap` (never empty). Because a wrong binary would only show as a container that never becomes healthy, the extracted tree is checked at deploy time for this runtime only: a regular `bootstrap` at the root (never a symlink), a Linux ELF of the function's architecture (`debug/elf` machine), static or linked against glibc with al2023's loader, or a `#!` script; a glibc-linked binary is deployed with the warning `FUNCTION_BOOTSTRAP_DYNAMIC` (recorded with the deployment, unknown codes dropped at load for forward compatibility), another loader is refused; `bootstrap` is forced executable (0555) whatever the zip says (Windows zips carry no Unix modes); other files keep the exec bit they have in the zip. A bootstrap that passes the checks but cannot start still fails the deploy (`up --wait`) and keeps the previous deployment.

### Runtime binary download (2026-11-06)

The table embedded in the build is filled with the first signed release (loch-lambda-runtime v1.0.1, amd64 and arm64: sha256 and size) and stays the only root of trust: the public key planned in the plan reviews is replaced by an informational `signing` object (cosign keyless identity of the release workflow and its OIDC issuer), because a keyless signature has no key to pin and verifying Sigstore bundles at run time would add a dependency without adding trust beyond the build-time hashes, which were checked against SHA256SUMS, its cosign signature and the GitHub provenance attestation before being added. The panel installs the newest trusted release of the host architecture by itself (startup in the background with backoff, then on demand), from `github.com` with redirects restricted to the GitHub asset hosts, HTTPS only, with its own client and the table's size as cap, or from `FUNCTIONS_RUNTIME_SOURCE_DIR` for offline installations (`FUNCTIONS_RUNTIME_DOWNLOAD=false` disables the download); the module stays usable meanwhile and answers `FUNCTION_RUNTIME_UNAVAILABLE` (503) to what needs the binary. Installs and refusals are audited.

### Consequences

- What stays specific to the panel is convenience (deployment interface, secrets injection, logs, audit), the same trade-off as the databases.
- The outbound side of Loch S3 is bounded by its networks: its instances are on `internal` networks and can only reach members of their private networks, which limits SSRF through the webhook target.
- A client-provided image runs client code on the host, as a hosted site already does: the isolation is the container constraints and the private networks, not trust in the code.
